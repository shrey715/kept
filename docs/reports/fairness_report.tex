\section{TL;DR}\label{tldr}

\textbf{No protected group gets materially different treatment.} Across
96,000 scored cases, the share of customers who get \emph{any} contact
action stays within a ratio of \textbf{0.86--1.00} between the lowest
and highest group of every protected attribute (the four-fifths rule
flags below 0.80).

The flags you'll see sit on \textbf{calls}, a rare action
(\textasciitilde3\% of cases), where tiny rates make ratios jumpy, and
on \textbf{hardship review}, which is \emph{supposed} to land more on
vulnerable customers. That's the protection doing its job.

\textbf{How this is possible:} protected attributes never go into a
decision. They live in \texttt{gold.c360\_restricted}, which only
compliance can read; a CI test fails the build if any model feature's
lineage touches one (or a proxy like postal code, age or language); and
a curated test suite checks the trained model's actual inputs. We use
them for exactly one thing: this report.

\section{What we read from it}\label{what-we-read-from-it}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Contact is even.} Gender, citizenship, household, dependants,
  benefits and accessibility all sit at 0.93--1.00 for ``any contact
  action''.
\item
  \textbf{Call flags are small-number noise.} Calls are
  \textasciitilde3\% of cards; 3.5\% vs 2.9\% is a 0.83 ratio but a tiny
  absolute gap.
\item
  \textbf{Vulnerable customers get more hardship reviews, on purpose.}
  The vulnerability \emph{flag} (a safeguard, not a protected attribute
  in the data dictionary) routes cases to protective actions. That shows
  up as a gap by \texttt{vulnerability\_type}, and it's the point.
\item
  \textbf{Blank attributes go with fewer contacts.} That's thin data
  (often holds, cease or the hold-out), not a group. Worth a
  data-coverage look, not a fairness fix.
\end{enumerate}
